# Virtualizing N5 containers

The N5 profile of [VIRTUALIZE.md](../VIRTUALIZE.md) (revision 16), numbered
as its §9. §1 is in VIRTUALIZE.md and applies here, in particular the store
input rules of §1.4–§1.6, and so does §2.

Profile version: 1 · Convention: [conventions/n5](../conventions/n5/README.md),
version 1. The output has the convention's layout for the input
([VIRTUALIZE.md §2](../VIRTUALIZE.md#2-the-zarr-layout)); this profile says
how the store is read, which inputs are rejected, and how each chunk
references the store. "The convention §n" below is a section of
conventions/n5/README.md.

## 9. N5 profile

The profile was chosen because the store's root has an `attributes.json`
(§1.4). The store is listed (§1.5), and its documents are read as JSON
(§1.6): the `attributes.json` of each candidate of
[the convention §2](../conventions/n5/README.md#2-nodes), which MUST be a
JSON object.

### 9.1 Rejection

The input is rejected when a rule of §1.4–§1.6 fails, and when the
convention gives it no layout: wherever it says that the input is
rejected, or that something MUST hold and it does not.

### 9.2 Chunks

Each chunk object is a chunk entry referencing the whole object (§1.4); an
object of size 0 has no entry. The block's header is not read: the output
depends only on the keys and sizes in the listing.

### 9.3 Summary

This section is informative. Both implementations print a one-line JSON
summary: `groups` (explicit and implicit), `arrays`, `chunks` (chunk
entries), `emptyChunks` (chunk objects of size 0), `objects` (the store's
objects), `images` (recognized groups, each `{"path", "convention"}`) and
`listingRequests`.
