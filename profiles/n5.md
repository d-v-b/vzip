# Virtualizing N5 containers

The N5 profile of [VIRTUALIZE.md](../VIRTUALIZE.md) (revision 16), numbered
as its §9. §1 is in VIRTUALIZE.md and applies here, in particular the store
input rules of §1.4–§1.6, and so does §2.

Profile version: 1 · Convention: [conventions/n5](../conventions/n5/README.md),
version 1. The output has the convention's layout for the input
([VIRTUALIZE.md §2](../VIRTUALIZE.md#2-the-zarr-layout)); this profile says
how the store is read, which inputs are rejected, and how each chunk
references the store. "The convention §n" below is a section of
conventions/n5/README.md.

## 9. N5 profile

The profile was chosen because the store's root has an `attributes.json`
(§1.4). The store is listed (§1.5), and its documents are read as JSON
(§1.6): the `attributes.json` of each candidate of
[the convention §2](../conventions/n5/README.md#2-nodes), which MUST be a
JSON object. Their integer literals are kept exactly where the convention
copies them ([its §5](../conventions/n5/README.md#5-source-metadata)),
beyond 2^53 − 1 too, in place of §1.6's last paragraph; every number the
convention uses is its binary64 value, as §1.6 says.

### 9.1 Rejection

The input is rejected when a rule of §1.4–§1.6 fails, and when the
convention gives it no layout: wherever it says that the input is
rejected, or that something MUST hold and it does not.

### 9.2 Chunks and other objects

Each chunk object is a chunk entry referencing the whole object (§1.4); an
object of size 0 has no entry, and its key is one of the convention §6's
empty objects' keys. The block's header is not read: the output
depends only on the keys and sizes in the listing.

Every other object of [the convention §6](../conventions/n5/README.md#6-other-objects)
is referenced whole in the same way, by an entry under the key
`vzip_source/objects/<k>` (with a `~` appended when the convention §6
escapes `k`'s last segment) whose `url` source is the URL of the object `k`
(§1.4). (This is the one place where an entry's key is not its object's
key; §1.4's rules otherwise apply: the sources are in ascending order of
their entries' keys, each entry referencing its object's whole range.)
Under a root array, the empty objects' keys and the ignored keys are the
document `vzip_source/empty.json` (the convention §6), written as UTF-8
compact JSON, as `JSON.stringify` writes it. The documents under
`vzip_source/` (which hold these keys) are deflated and, like the chunks, not
among the documents a reader fetches when it opens the archive
([conventions §2](../conventions/README.md#2-attributes)).

### 9.3 Summary

This section is informative. Both implementations print a one-line JSON
summary: `groups` (explicit and implicit), `arrays`, `chunks` (chunk
entries), `emptyChunks` (chunk objects of size 0), `objects` (the store's
objects), `otherObjects` (the entries under `vzip_source/objects/`),
`images` (recognized groups, each `{"path", "convention"}`) and
`listingRequests`.
